# Broker Order API

## Overview

The Mini Exchange API Gateway exposes a broker-facing HTTP interface for
submitting and querying limit orders, plus public market data endpoints. The
gateway is currently **in-memory** with no database persistence.

The broker identifier is supplied in the URL path:

```
/api/v1/brokers/{broker_id}/orders
```

There is **no real authentication yet**. In production, broker identity should
come from API keys, OAuth tokens, JWT, mTLS, or another authentication layer.

## Health

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/health/live` | Liveness probe — returns `{"status":"ok"}` |
| `GET` | `/health/ready` | Readiness probe — returns `{"status":"ok"}` |

## Order endpoints

### Submit Order

```
POST /api/v1/brokers/{broker_id}/orders
```

Creates a new limit order for the given broker.

**Request body** (`application/json`):

| Field             | Type            | Required | Notes                                      |
|-------------------|-----------------|----------|--------------------------------------------|
| client_order_id   | string \| null  | No       | Broker-scoped idempotency key (max 128)    |
| document_number   | string          | Yes      | Customer owner ID (3-32 chars); not the broker ID |
| side              | string          | Yes      | `BID` or `ASK`                             |
| valid_until       | datetime \| null| No       | `null` = GTC (no expiration); otherwise timezone-aware UTC |
| symbol            | string          | Yes      | Max 16 chars, normalized to uppercase      |
| price             | integer         | Yes      | Strict positive integer (cents)            |
| quantity          | integer         | Yes      | Strict positive integer                    |

**Success response**: `201 Created`

### Get Order Status

```
GET /api/v1/brokers/{broker_id}/orders/{order_id}
```

Returns the latest status for an order owned by the given broker.

**Success response**: `200 OK`

### Response Fields

Both order endpoints return `OrderResponse`:

| Field              | Type               | Notes                        |
|--------------------|--------------------|------------------------------|
| order_id           | string             | Generated by the engine      |
| broker_id          | string             | From the URL path            |
| client_order_id    | string \| null     | Echo of request field        |
| document_number    | string             | Submitted customer document (not broker ID) |
| side               | string             | `BID` or `ASK`              |
| symbol             | string             | Normalized uppercase         |
| price              | integer            | Original order price (cents) |
| quantity           | integer            | Original order quantity      |
| remaining_quantity | integer            | Unfilled quantity            |
| filled_quantity    | integer            | Executed quantity            |
| status             | string             | See status values below      |
| valid_until        | datetime \| null   | `null` for GTC orders        |
| trades             | array[Trade]       | Trades involving this order  |

### Broker vs customer identity

- **`broker_id`** (URL path): the broker submitting the order.
- **`document_number`** (request body): the customer who owns the order.

The gateway passes `document_number` to the matching core as customer ownership
identity. Self-trade prevention compares customer documents, not broker IDs.

### Self-trade prevention

Orders with the same `document_number` do not match each other, even when
submitted by different brokers. Different customer documents may trade when
prices cross.

## Market data endpoints

Public read-only endpoints (no broker path). Symbol is normalized to uppercase.

### Order book snapshot

```
GET /api/v1/market/{symbol}/book?depth={n}
```

Returns aggregated bid and ask levels for the symbol.

| Query param | Type | Default | Notes |
|-------------|------|---------|-------|
| depth       | int  | all     | Optional, 1–50 levels per side |

**Response** (`BookSnapshotResponse`):

| Field  | Type | Notes |
|--------|------|-------|
| symbol | string | Uppercase symbol |
| bids   | array | `{ price, quantity }` sorted best bid first |
| asks   | array | `{ price, quantity }` sorted best ask first |

### Recent trades

```
GET /api/v1/market/{symbol}/trades?limit={n}
```

Returns recent trades for the symbol, newest first.

| Query param | Type | Default | Notes |
|-------------|------|---------|-------|
| limit       | int  | 50      | 1–200 |

**Response** (`MarketTradesResponse`):

| Field  | Type | Notes |
|--------|------|-------|
| symbol | string | Uppercase symbol |
| trades | array | `{ trade_id, sequence, symbol, price, quantity }` |

Market trade responses intentionally omit broker IDs and document numbers.

## Side Values

- **BID** — buy order. The price is the buyer's **maximum** price.
- **ASK** — sell order. The price is the seller's **minimum** price.

The execution price is **always the seller order price**.

## Prices and Quantities

All prices and quantities are **integers**. Do not use floats for money.
The UI accepts USD decimals (e.g. `10.50`) and converts to cents (`1050`).

## Order Validity

- **`valid_until: null`** — GTC (Good Till Cancelled). The order is never
  expired automatically. In this in-memory MVP it remains until filled, future
  cancellation support, or process restart.
- **`valid_until: <datetime>`** — Must be timezone-aware (normalized to UTC).
  Must be in the future at submission time. Resting orders whose
  `valid_until` has passed are expired lazily on the next submit or status
  retrieval operation.

## Idempotency

Broker-scoped idempotency is supported via `client_order_id`. If the same
broker submits the same `client_order_id` with identical parameters, the
original order response is returned without creating a new order. If the
parameters differ, a `409 Conflict` is returned.

## Status Codes

| Code | Meaning                                  |
|------|------------------------------------------|
| 201  | Order submitted successfully             |
| 200  | Order status or market data retrieved    |
| 400  | Expired order submission                 |
| 404  | Unknown order or wrong broker            |
| 409  | Idempotency conflict                     |
| 422  | Request validation error                 |

Returning 404 for an order owned by a different broker is intentional to avoid
leaking order existence.

## Order Statuses

| Status            | Meaning                              |
|-------------------|--------------------------------------|
| OPEN              | Resting, no fills yet                |
| PARTIALLY_FILLED  | Some quantity filled, rest resting   |
| FILLED            | Fully executed                       |
| CANCELED          | Canceled by broker                   |
| EXPIRED           | Validity window elapsed              |

## Examples

### GTC order (no expiration)

```bash
curl -X POST http://localhost:8000/api/v1/brokers/seller-1/orders \
  -H "Content-Type: application/json" \
  -d '{
    "document_number": "11111111100",
    "side": "ASK",
    "valid_until": null,
    "symbol": "AAPL",
    "price": 1000,
    "quantity": 10
  }'
```

### Matching ASK and BID

Submit an ASK at price 1000, then a BID at price 2000. The trade executes at
1000 because the execution price is always the seller order price.

```bash
# Seller places ASK at 1000
curl -X POST http://localhost:8000/api/v1/brokers/seller-1/orders \
  -H "Content-Type: application/json" \
  -d '{
    "document_number": "11111111100",
    "side": "ASK",
    "valid_until": "2030-01-01T00:00:00Z",
    "symbol": "AAPL",
    "price": 1000,
    "quantity": 10
  }'

# Buyer places BID at 2000 — matches at seller price 1000
curl -X POST http://localhost:8000/api/v1/brokers/buyer-1/orders \
  -H "Content-Type: application/json" \
  -d '{
    "document_number": "22222222200",
    "side": "BID",
    "valid_until": "2030-01-01T00:00:00Z",
    "symbol": "AAPL",
    "price": 2000,
    "quantity": 10
  }'
```

The second response will include `"status": "FILLED"` and a trade at price `1000`.

### Market data

```bash
curl http://localhost:8000/api/v1/market/AAPL/book
curl "http://localhost:8000/api/v1/market/AAPL/trades?limit=20"
```
