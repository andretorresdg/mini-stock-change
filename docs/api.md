# Broker Order API

## Overview

The Mini Exchange API Gateway exposes a broker-facing HTTP interface for
submitting and querying limit orders. The gateway is currently **in-memory**
with no database persistence.

The broker identifier is supplied in the URL path:

```
/api/v1/brokers/{broker_id}/orders
```

There is **no real authentication yet**. In production, broker identity should
come from API keys, OAuth tokens, JWT, mTLS, or another authentication layer.

## Endpoints

### Submit Order

```
POST /api/v1/brokers/{broker_id}/orders
```

Creates a new limit order for the given broker.

**Request body** (`application/json`):

| Field             | Type          | Required | Notes                                      |
|-------------------|---------------|----------|--------------------------------------------|
| client_order_id   | string\|null  | No       | Broker-scoped idempotency key (max 128)    |
| document_number   | string        | Yes      | 3-32 chars, letters/digits/dots/dashes/slashes |
| side              | string        | Yes      | `BID` or `ASK`                             |
| valid_until       | datetime      | Yes      | Must be timezone-aware (normalized to UTC) |
| symbol            | string        | Yes      | Max 16 chars, normalized to uppercase      |
| price             | integer       | Yes      | Strict positive integer                    |
| quantity          | integer       | Yes      | Strict positive integer                    |

**Success response**: `201 Created`

### Get Order Status

```
GET /api/v1/brokers/{broker_id}/orders/{order_id}
```

Returns the latest status for an order owned by the given broker.

**Success response**: `200 OK`

### Response Fields

Both endpoints return `OrderResponse`:

| Field              | Type               | Notes                        |
|--------------------|--------------------|------------------------------|
| order_id           | string             | Generated by the engine      |
| broker_id          | string             | From the URL path            |
| client_order_id    | string\|null       | Echo of request field        |
| document_number    | string             | Echo of request field        |
| side               | string             | `BID` or `ASK`              |
| symbol             | string             | Normalized uppercase         |
| price              | integer            | Original order price         |
| quantity           | integer            | Original order quantity      |
| remaining_quantity | integer            | Unfilled quantity            |
| filled_quantity    | integer            | Executed quantity            |
| status             | string             | See status values below      |
| valid_until        | datetime           | UTC normalized               |
| trades             | array[Trade]       | Trades involving this order  |

### Trade Fields

| Field             | Type    |
|-------------------|---------|
| trade_id          | string  |
| sequence          | integer |
| symbol            | string  |
| buyer_order_id    | string  |
| seller_order_id   | string  |
| buyer_broker_id   | string  |
| seller_broker_id  | string  |
| price             | integer |
| quantity          | integer |

## Side Values

- **BID** — buy order. The price is the buyer's **maximum** price.
- **ASK** — sell order. The price is the seller's **minimum** price.

The execution price is **always the seller order price**.

## Prices and Quantities

All prices and quantities are **integers**. Do not use floats for money.

## Order Validity

`valid_until` must be timezone-aware. Resting orders whose `valid_until` has
passed are expired lazily on the next submit or status retrieval operation.

## Idempotency

Broker-scoped idempotency is supported via `client_order_id`. If the same
broker submits the same `client_order_id` with identical parameters, the
original order response is returned without creating a new order. If the
parameters differ, a `409 Conflict` is returned.

## Status Codes

| Code | Meaning                                  |
|------|------------------------------------------|
| 201  | Order submitted successfully             |
| 200  | Order status retrieved successfully      |
| 400  | Expired order submission                 |
| 404  | Unknown order or wrong broker            |
| 409  | Idempotency conflict                     |
| 422  | Request validation error                 |

Returning 404 for an order owned by a different broker is intentional to avoid
leaking order existence.

## Order Statuses

| Status            | Meaning                              |
|-------------------|--------------------------------------|
| OPEN              | Resting, no fills yet                |
| PARTIALLY_FILLED  | Some quantity filled, rest resting   |
| FILLED            | Fully executed                       |
| CANCELED          | Canceled by broker                   |
| EXPIRED           | Validity window elapsed              |

## Example

Submit an ASK at price 1000, then a BID at price 2000. The trade executes at
1000 because the execution price is always the seller order price.

```bash
# Seller places ASK at 1000
curl -X POST http://localhost:8000/api/v1/brokers/seller-1/orders \
  -H "Content-Type: application/json" \
  -d '{
    "document_number": "DOC-001",
    "side": "ASK",
    "valid_until": "2030-01-01T00:00:00Z",
    "symbol": "AAPL",
    "price": 1000,
    "quantity": 10
  }'

# Buyer places BID at 2000 — matches at seller price 1000
curl -X POST http://localhost:8000/api/v1/brokers/buyer-1/orders \
  -H "Content-Type: application/json" \
  -d '{
    "document_number": "DOC-002",
    "side": "BID",
    "valid_until": "2030-01-01T00:00:00Z",
    "symbol": "AAPL",
    "price": 2000,
    "quantity": 10
  }'
```

The second response will include:

```json
{
  "order_id": "AAPL-2",
  "status": "FILLED",
  "trades": [
    {
      "trade_id": "AAPL-T1",
      "price": 1000,
      "quantity": 10,
      "buyer_order_id": "AAPL-2",
      "seller_order_id": "AAPL-1"
    }
  ]
}
```
